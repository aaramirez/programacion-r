Gráficos dinámicos e htmlwidgets

Cecilia no quiere un PNG: quiere pasar el ratón por una estación y saber cuántas bicis pierde cada mañana, acercar el mapa a Las Lomas y filtrar la tabla. Los htmlwidgets hacen eso sin servidor: R escribe una página con los datos y una biblioteca de JavaScript, y el navegador hace el resto. En este capítulo los widgets se fabrican de verdad con R en la página.

Qué es un htmlwidget: R que escribe JavaScript

Cecilia Mora, la coordinadora de la flota, vio los gráficos del capítulo 07 y le hizo a Gabriela tres preguntas seguidas: «¿Cuál es esa estación que gana once bicis? ¿Puedo ver solo junio? ¿Y si quiero las estaciones de Las Lomas en un mapa?». Con un PNG, cada pregunta es un gráfico nuevo. Lo que Cecilia quiere es poder preguntarle al gráfico directamente: pasar el ratón, acercar, filtrar.

Los navegadores llevan años haciendo eso con bibliotecas de JavaScript, el lenguaje que corre dentro de cada página web: plotly.js para gráficos, Leaflet para mapas, DataTables para tablas. El problema es que hay que escribir JavaScript, y Gabriela escribe R. Los htmlwidgets resuelven eso: son paquetes de R que, por dentro, escriben la página web por ti.

Imagínalo así

Piensa en una caja de muebles para armar. La fábrica no te manda el mueble armado: te manda las piezas, los tornillos y el instructivo en la misma caja, y el armado lo haces tú en tu casa. Un htmlwidget es la caja: R prepara las piezas (los datos), mete el instructivo (la biblioteca de JavaScript) y el navegador arma el gráfico al abrir la página. Una vez armado, el mueble ya no necesita a la fábrica: el gráfico responde al ratón sin R.

Un htmlwidget es un objeto de R con tres partes. Una lista llamada x con los datos y las opciones del gráfico. Una lista de dependencias (dependencies): los archivos de JavaScript y CSS que necesita, que vienen copiados dentro del paquete de R. Y un ancho y un alto. Cuando lo imprimes en RStudio o Positron, o lo guardas con htmlwidgets::saveWidget(), el paquete htmlwidgets convierte x a JSON (JavaScript Object Notation, notación de objetos de JavaScript), un formato de texto que cualquier navegador entiende, y escribe una página con un <div> vacío, el JSON y las bibliotecas.

Esa última frase es la clave del capítulo. R participa solo hasta escribir el archivo. Después, el widget es una página web autónoma: se puede mandar por correo, insertar en un documento Quarto (capítulo 09) o publicar en GitHub Pages, y funciona sin R instalado y sin servidor. La contracara es que no puede volver a preguntarle nada a R: si Cecilia quiere recalcular con otro período, el widget no puede; para eso hace falta Shiny, desde el capítulo 10.

El paquete htmlwidgets es el marco común: define cómo se empaquetan las dependencias y cómo se pasa el JSON, y cada paquete de widgets (plotly, leaflet, DT, dygraphs y decenas más) agrega su enlace (binding): unas líneas de JavaScript que reciben el JSON y llaman a la biblioteca. Por eso todos se usan igual desde R y todos funcionan en los mismos lugares.

Una nota sobre los laboratorios de este capítulo: los widgets que vas a ver los hace R de verdad, en tu navegador, con webR. El paquete de R escribe la página con su JSON y sus bibliotecas (las mismas que instalarías en tu equipo) y el laboratorio la muestra en un recuadro. Antes de cargar R ves una captura fija, sin interacción. La primera carga es lenta (plotly y sus dependencias pesan unos 20 MB más), y después cada ejecución tarda un par de segundos.

plotly y ggplotly(): un ggplot que responde al ratón

plotly es una biblioteca de gráficos interactivos de código abierto, con versiones para JavaScript, Python y R. El paquete de R tiene dos puertas de entrada. La primera es ggplotly(): recibe un ggplot ya hecho y lo traduce, capa por capa, a plotly.js. Es la manera más rápida de volver interactivo lo que ya sabes hacer:

g <- ggplot(h, aes(hora, salidas, color = tipo_dia)) + geom_line() + geom_point()
ggplotly(g)

El resultado trae de regalo una etiqueta al pasar el ratón (tooltip) con los valores de cada estética, el zoom con un rectángulo, el doble clic para volver, una leyenda en la que un clic oculta una serie y una barra de herramientas para descargar un PNG. Si quieres decidir qué dice la etiqueta, asigna la estética text en el ggplot (ggplot2 la ignora y avisa) y pide ggplotly(g, tooltip = "text").

La traducción no es perfecta: algunas geometrías y extensiones de ggplot2 no tienen equivalente en plotly.js y se pierden o se dibujan distinto, y los temas muy personalizados no siempre sobreviven. La segunda puerta, plot_ly(), habla directo con plotly.js: plot_ly(e, x = ~salidas, y = ~nombre, color = ~barrio, type = "bar"). La virgulilla (~) dice «esta columna de la tabla». Es menos conocida, pero da acceso a todo lo que plotly.js sabe hacer, como gráficos 3D, ejes enlazados o animaciones con un deslizador, y se configura con layout().

# cap08.R · Tres htmlwidgets de RiberaBici en archivos HTML (capítulo 08)
# Usa la tabla v que dejó cap07.R: corre antes source("cap07.R")
library(ggplot2)
library(plotly)
library(leaflet)
library(htmlwidgets)
dir.create("widgets", showWarnings = FALSE)

# 1. El perfil por hora: un ggplot convertido a plotly
h <- aggregate(viaje_id ~ hora + tipo_dia, v, length)
names(h)[3] <- "viajes"
g <- ggplot(h, aes(hora, viajes, color = tipo_dia)) +
  geom_line() + geom_point() +
  labs(x = "Hora", y = "Viajes", color = NULL) + theme_minimal()
saveWidget(ggplotly(g), "widgets/perfil.html", selfcontained = FALSE, libdir = "lib")

# 2. El mapa de estaciones, con el neto de la mañana en color
est <- read.csv("datos/estaciones.csv")
lab <- v[v$tipo_dia == "laborable" & v$hora >= 6 & v$hora < 10, ]
n_lab <- length(unique(as.Date(lab$inicio)))
est$neto_manana <- round(as.numeric(
  table(factor(lab$estacion_destino, levels = est$estacion_id)) -
  table(factor(lab$estacion_origen,  levels = est$estacion_id))) / n_lab, 1)
pal <- colorNumeric("RdBu", domain = c(-11, 11))
m <- leaflet(est) |>
  addProviderTiles("Esri.WorldGrayCanvas") |>
  addCircleMarkers(~lon, ~lat, radius = 8, color = ~pal(neto_manana),
                   fillOpacity = 0.9, stroke = FALSE,
                   label = ~paste(estacion_id, nombre, neto_manana)) |>
  addLegend(pal = pal, values = ~neto_manana, title = "Neto mañana")
saveWidget(m, "widgets/mapa.html", selfcontained = FALSE, libdir = "lib")

# 3. Cuánto pesa cada parte
cat("Archivos HTML:\n"); print(file.size(list.files("widgets", "html$", full.names = TRUE)))
cat("Bibliotecas copiadas en widgets/lib:\n"); print(list.files("widgets/lib"))

Qué observar: los dos HTML pesan poco (unos 4 KB el mapa y 7 KB el perfil) porque solo llevan el <div> y el JSON; lo pesado está en widgets/lib, donde R copió plotly.js, Leaflet, jQuery, htmlwidgets y crosstalk, una carpeta por biblioteca y versión. Dentro del <script type="application/json"> ves tus datos convertidos a texto: las horas, los viajes, las coordenadas de las 24 estaciones. Si mandas el HTML sin la carpeta lib, no se dibuja nada. Con selfcontained = TRUE R mete todo en un solo archivo, pero para eso necesita Pandoc, que viene con RStudio y con Quarto.


Mapas con leaflet
Leaflet es la biblioteca de mapas interactivos más usada en la web, y el paquete leaflet de R la envuelve con funciones que se encadenan con la tubería. Un mapa se arma como un ggplot, por capas, solo que con |> en vez de +: leaflet(datos) crea el mapa, addTiles() o addProviderTiles() agregan el fondo, addCircleMarkers() o addMarkers() agregan los puntos, addPolygons() las áreas y addLegend() la leyenda.
Imagínalo así
Un mapa web es como un álbum de fotos aéreas cortadas en cuadritos. Nadie descarga la foto del planeta entero: según dónde mires y cuánto acerques, el navegador pide solo los cuadritos que necesita, y al acercar pide otros con más detalle. Encima de ese álbum, Leaflet pega tus propias calcomanías: los círculos de las estaciones.
Esos cuadritos se llaman mosaicos (tiles): imágenes de 256 × 256 píxeles que un servidor de mapas entrega según el nivel de zoom y la posición. addTiles() usa los de OpenStreetMap, el mapa colaborativo y abierto del mundo; addProviderTiles("Esri.WorldGrayCanvas") usa un fondo gris claro que no compite con los datos, y la lista providers del paquete trae decenas más. Cada proveedor tiene sus condiciones de uso y pide que se le dé crédito, que Leaflet pone en la esquina; algunos, además, piden una clave de API (a noviembre de 2026, los fondos de CARTO, por ejemplo, muestran «API KEY REQUIRED» sin ella). Un mapa puede no tener fondo: con solo los círculos se ven las posiciones relativas, sin pedir nada a internet.
Las estéticas de leaflet se escriben con fórmulas: radius = ~sqrt(salidas) / 6 dice «el radio sale de la columna salidas». Para el color hay funciones que construyen una paleta a partir de los datos: colorFactor() para categorías, colorNumeric() para números con un degradado continuo, colorBin() y colorQuantile() para cortarlos en tramos. La misma paleta se le pasa después a addLegend(), así el color del mapa y el de la leyenda coinciden.
Las coordenadas de Ciudad Ribera son inventadas y caen en una llanura poco poblada: si usas un fondo con calles, el mapa muestra campo y pueblos que no tienen nada que ver con RiberaBici. Es un buen recordatorio de que el mapa base es solo contexto; lo que importa son las capas de datos.

Tablas interactivas con DT y reactable
Una tabla de 24 estaciones no cabe cómoda en un gráfico, y a veces lo que la persona quiere es justamente eso: la tabla, para ordenarla por la columna que le importa y buscar una estación por nombre. DT envuelve DataTables, una biblioteca de JavaScript para tablas: datatable(e) da una tabla paginada, con orden al hacer clic en la cabecera y una caja de búsqueda. Con filter = "top" agrega un filtro por columna (un rango para los números, una lista para el texto), y con options = list(...) se le pasa cualquier opción de DataTables, como pageLength o scrollX.
reactable hace lo mismo con otra biblioteca, React Table, y pone el acento en el formato: cada columna se define con colDef(), que acepta funciones de R para dar estilo celda por celda (rojo si el balance es negativo, una barra dentro de la celda), filas que se expanden con un detalle y grupos que se pliegan. La función de estilo se evalúa en R antes de enviar la tabla, así que el navegador recibe el color ya decidido.
Las dos tienen un límite: todos los datos viajan dentro de la página. Con unos miles de filas no hay problema; con los 70.796 viajes, la página pesaría varios megabytes y tardaría en abrir. Para tablas grandes se muestra un resumen, o se usa DT dentro de Shiny en modo servidor, que manda solo la página de filas que se está viendo.


Series de tiempo con dygraphs
dygraphs está hecho para una sola cosa: series de tiempo largas, con muchas observaciones por fecha. Recibe un objeto xts (eXtensible Time Series), una tabla cuyas filas están indexadas por fecha, y dibuja una o varias líneas con un selector de rango (range selector) abajo: una miniatura de toda la serie con dos bordes que se arrastran para elegir el período. La etiqueta sigue al ratón y muestra todos los valores de esa fecha a la vez.
Las opciones se encadenan: dySeries() configura cada serie (su rótulo, si va al eje derecho con axis = "y2", si se dibuja en escalones); dyRangeSelector() agrega el selector; dyShading() sombrea un período, como las vacaciones de julio; dyEvent() marca una fecha con una línea vertical, como la apertura de E24 el 1 de junio; dyRoller() agrega una media móvil que el lector ajusta. En la serie diaria de RiberaBici, el selector permite mirar solo junio, el mes más lluvioso, y ver cada valle de viajes sobre un escalón de lluvia.


Animaciones con gganimate
A veces lo que se quiere mostrar es un cambio en el tiempo y no hay nadie que vaya a interactuar: una lámina en una presentación, un mensaje en una red social. gganimate agrega a ggplot2 una gramática de la animación: escribes un ggplot normal y le sumas una transición que dice cómo cambia de un cuadro a otro. transition_time(hora) hace un cuadro por hora e interpola entre ellos; transition_states() pasa entre estados con pausas; transition_reveal() va dibujando una línea a medida que avanza el tiempo. En el título, {frame_time} se reemplaza por el valor de cada cuadro.
gganimate no es un htmlwidget: no produce JavaScript. animate() dibuja cada cuadro con R y los junta en un GIF (con el paquete gifski) o en un video (con av o ffmpeg). El resultado se anima solo, pero no responde al ratón. Por eso conviene pensar antes: si el lector va a explorar, widget; si va a mirar pasar, animación.

El mapa de las salidas de cada hora, animado
Vas a animar con gganimate las salidas de los días laborables estación por estación, hora por hora: el mapa del sistema que se enciende a las 7 y a las 17. Usa la tabla v que dejó cap07.R en tu sesión de R. Necesitas gganimate y gifski (los instalaste en la práctica anterior). Tarda unos segundos: dibuja 36 cuadros.
  1. Guarda este guion como ~/bicis/cap08-anim.R:
# cap08-anim.R · Los viajes de cada hora, animados con gganimate (capítulo 08)
# Usa la tabla v que dejó cap07.R: corre antes source("cap07.R")
library(ggplot2)
library(gganimate)

est <- read.csv("datos/estaciones.csv")
lab <- v[v$tipo_dia == "laborable", ]
s <- aggregate(viaje_id ~ estacion_origen + hora, lab, length)
names(s) <- c("estacion_id", "hora", "salidas")
s <- merge(s, est[, c("estacion_id", "lon", "lat", "barrio")])

a <- ggplot(s, aes(lon, lat, size = salidas, color = barrio)) +
  geom_point(alpha = 0.8) +
  scale_size_area(max_size = 14) +
  coord_quickmap() +
  labs(title = "Salidas en días laborables, hora: {frame_time}:00",
       x = NULL, y = NULL, size = "Salidas", color = "Barrio") +
  theme_minimal() +
  transition_time(hora)
anim_save("cap08-horas.gif", animate(a, nframes = 36, fps = 4, width = 640, height = 480))
  1. Córrelo en la consola de R y abre cap08-horas.gif con cualquier visor de imágenes o con el navegador:
source("cap08-anim.R")
Qué observar: el título cuenta las horas; algunas salen con decimales («6.4:00»), porque transition_time interpola entre horas para que el movimiento sea suave (con transition_states(hora) saltaría de una hora a la siguiente). A las 7 se encienden los círculos de Las Lomas y de Ribera, de donde sale la gente por la mañana; a las 17 crecen los del Centro y la Universidad, de donde vuelven. Entre medio, casi todo se apaga. Es el mismo patrón de los dos picos, contado como movimiento. El GIF se puede pegar en una presentación, pero nadie puede pasar el ratón por un círculo para saber su nombre.


Gráficos enlazados sin servidor con crosstalk
El último pedido de Cecilia es el más interesante: quiere marcar en un gráfico las estaciones que pierden bicis y verlas en el mapa. Eso es enlazar (linked brushing): una selección en un widget se refleja en otro. Lo natural sería pensar en un servidor que reciba la selección y redibuje el mapa, pero crosstalk lo hace sin servidor, dentro de la página.
Imagínalo así
Imagina dos personas mirando la misma lista de invitados impresa, cada una desde su escritorio. Si una marca con resaltador «Mesa 4: López, Pérez, Rivas», la otra no necesita llamar a nadie para saber de quiénes se trata: basta con que le griten los apellidos. crosstalk es ese grito. Los dos widgets tienen la misma tabla, y lo único que se pasan son las claves de las filas elegidas.
La pieza central es SharedData$new(e, key = ~estacion_id): envuelve la tabla y le da una clave (key) por fila. Si le pasas ese objeto, en lugar de la tabla, a varios widgets compatibles (plotly, leaflet y DT, entre otros), todos quedan conectados. Cuando el lector selecciona puntos en plotly, crosstalk.js transmite en la página «seleccionadas: E10, E11, E12, E13», y el mapa y la tabla resaltan esas claves. Los filtros (filter_checkbox(), filter_slider(), filter_select()) funcionan igual: ocultan filas en todos los widgets a la vez. bscols() los acomoda en columnas.
crosstalk tiene límites claros, y conviene decirlos antes de prometer un tablero. Solo selecciona y filtra filas que ya están en la página: no agrega, no recalcula promedios para la selección, no ajusta modelos. Todos los datos viajan en el HTML, así que sirve para cientos o unos pocos miles de filas. Y no todos los widgets lo entienden. Cuando el pedido pasa de «marcar y ver» a «calcular con lo que marqué», se necesita Shiny.

Un caso real
Los gráficos interactivos del periodismo de datos. Los grandes diarios publican desde hace más de una década gráficos interactivos en sus artículos: mapas electorales que se acercan barrio por barrio, tablas que se ordenan, series que el lector recorre con el ratón. Muchos se hacen exactamente como en este capítulo: los datos se preparan con R o Python, se generan como una página estática con sus bibliotecas de JavaScript y se publican sin servidor de cálculo, porque una página estática aguanta millones de visitas en un día de elecciones y un servidor de R no. La regla que usan esos equipos sirve para cualquier tablero: lo que se puede calcular de antemano se calcula antes y se publica como página; el servidor se reserva para lo que de verdad depende de lo que pide el lector.

La idea clave
Un htmlwidget es R que escribe JavaScript: el paquete convierte los datos a JSON, los mete en una página junto con una biblioteca de JavaScript (plotly.js, Leaflet, DataTables, dygraphs) y el navegador arma el gráfico. Desde ahí, pasar el ratón, acercar, ordenar o filtrar ocurre en el cliente, sin R y sin servidor, y la página se puede mandar o publicar como cualquier archivo. crosstalk enlaza varios widgets por una clave común para que una selección en uno se vea en los demás. El límite es el mismo para todos: el widget solo conoce los datos que viajaron en la página. Cuando hay que recalcular, hace falta Shiny.


Pruébate
Pruébate
¿Qué tres partes tiene un objeto htmlwidget en R?
Los datos y opciones (x, una lista que se convierte a JSON), las dependencias (las bibliotecas de JavaScript y CSS que vienen con el paquete) y el tamaño (ancho y alto).
Mandas por correo perfil.html, guardado con selfcontained = FALSE, y tu jefe ve una página en blanco. ¿Qué pasó?
Le faltó la carpeta lib con las bibliotecas de JavaScript: el HTML solo tiene el <div> y el JSON. Hay que mandar la carpeta o guardar con selfcontained = TRUE, que mete todo en un archivo (necesita Pandoc).
¿Para qué sirve la estética text en un ggplot que vas a pasar por ggplotly()?
Para decidir qué dice la etiqueta al pasar el ratón: ggplot2 la ignora, pero ggplotly(g, tooltip = "text") la usa.
¿Qué hace colorNumeric("RdBu", domain = c(-11, 11)) en un mapa de leaflet?
Crea una función de paleta que convierte números entre −11 y 11 en colores de rojo a azul, con el blanco en el cero. Se usa en color = ~pal(neto_manana) y en addLegend() para que el mapa y la leyenda coincidan.
¿Por qué crosstalk no sirve para mostrar el promedio de viajes de las estaciones que seleccionó el lector?
Porque solo selecciona y filtra filas que ya están en la página; no recalcula nada. Para un cálculo con la selección hace falta un servidor, como Shiny.
¿En qué se diferencia gganimate de los htmlwidgets?
gganimate dibuja cada cuadro con R y produce un GIF o un video que se anima solo; no hay JavaScript ni interacción con el ratón.
