La primera aplicación Shiny

Ernesto ya no quiere otro gráfico por correo: quiere mover él mismo la hora, el barrio y las fechas. Este capítulo convierte el análisis de los viajes en una aplicación web con Shiny: una interfaz que se declara, un servidor que responde, las entradas y salidas más usadas, un diseño con bslib y la misma idea en Python.

Qué es Shiny y qué problema resuelve

Un lunes, Ernesto Salas le escribe a Gabriela Rondón: «¿Me mandas los viajes por hora, pero solo de Las Lomas?». Gabriela cambia una línea de su guion, guarda el gráfico y se lo envía. A la media hora llega otro correo: «¿Y solo en la mañana? ¿Y si dejo afuera agosto?». Cada pregunta nueva es otro gráfico hecho a mano. El análisis está bien; lo que falla es el camino: Ernesto depende de Gabriela para cada variante de la misma pregunta.

La salida es darle a Ernesto los controles. En lugar de mandarle el resultado, Gabriela le manda una página donde él elige la hora, el barrio y las fechas, y el gráfico se rehace solo. Eso es una aplicación web (web application): un programa que se usa desde el navegador, sin instalar nada.

Imagínalo así

Piensa en un restaurante. El menú es lo que el cliente ve y donde elige: no cocina nada, solo ofrece opciones. La cocina recibe el pedido, prepara el plato y lo devuelve. El mesero lleva y trae. En Shiny, el menú es la interfaz, la cocina es el servidor que corre tu código de R y el mesero es una conexión que lleva cada elección y trae cada resultado. Ernesto pide desde el menú; Gabriela solo escribió la carta y la receta una vez.

Shiny es un paquete de R para escribir aplicaciones web solo con R. Lo presentó RStudio (hoy Posit) en 2012, y su idea central es que quien analiza datos no tenga que aprender HTML, CSS ni JavaScript para publicar una herramienta. Tú describes la página con funciones de R (un deslizador, una lista, un hueco para un gráfico) y escribes el código que calcula cada resultado. Shiny traduce la descripción a HTML, abre la conexión con el navegador y decide cuándo volver a correr cada parte de tu código.

Esa última frase es la que hace a Shiny distinto de un guion. Un guion corre de arriba abajo una vez. Una aplicación Shiny queda viva, esperando, y cuando Ernesto mueve el deslizador vuelve a ejecutar solo lo que depende de ese deslizador. El capítulo 11 explica cómo lo decide; aquí basta saber que lo hace.

Hay dos maneras de poner a correr una aplicación, y conviene distinguirlas desde el principio:

  • Shiny con servidor. Un proceso de R corre en una máquina (tu computador mientras desarrollas; en producción, un servicio como Posit Connect, shinyapps.io o un contenedor, que verás en el capítulo 13). Cada persona que abre la página recibe una sesión (session) propia en ese proceso. Los datos nunca salen del servidor: el navegador solo recibe el gráfico ya dibujado.
  • Shinylive. La aplicación entera, con R incluido, se descarga al navegador y corre ahí gracias a webR, el R compilado a WebAssembly que ya conoces del capítulo 01. No hace falta servidor: basta un sitio estático como GitHub Pages. A cambio, la primera carga pesa decenas de megabytes, solo funcionan los paquetes compilados para webR y los datos viajan al navegador de cada visitante, así que no sirve para datos confidenciales.

Los laboratorios de este capítulo usan Shinylive porque así la aplicación corre en la página sin instalar nada. Shinylive es un servicio gratuito de Posit que corre la aplicación en tu navegador con webR; no hay servidor. Las prácticas, en cambio, corren Shiny con servidor en tu propio equipo, que es como trabajarás de verdad.

La interfaz (ui) y el servidor (server)

Toda aplicación Shiny tiene dos partes y una línea que las une. Puede vivir en un solo archivo, app.R, que es la forma recomendada para empezar:

library(shiny)

ui <- fluidPage(
  sliderInput("hora", "Desde la hora", min = 6, max = 23, value = 7),
  plotOutput("grafico")
)

server <- function(input, output) {
  output$grafico <- renderPlot({
    v <- viajes[viajes$hora >= input$hora, ]
    hist(v$duracion_min)
  })
}

shinyApp(ui, server)

La interfaz (user interface, ui) es un objeto, no una función: describe qué se ve. fluidPage() arma una página, sliderInput() pone un deslizador y plotOutput() deja un hueco vacío donde irá un gráfico. Si imprimes ui en la consola, verás el HTML que genera: Shiny es, en esa parte, un traductor de funciones de R a etiquetas HTML.

El servidor (server) es una función con dos argumentos, input y output, que Shiny llama una vez por cada sesión. input es una lista de solo lectura con el valor actual de cada entrada: input$hora vale lo que marque el deslizador en ese momento. output es una lista donde tú asignas: a cada output$nombre le das el resultado de una función render*(), que contiene el código que produce esa salida. Al final, shinyApp(ui, server) junta las dos partes y arranca.

Tres reglas evitan casi todos los tropiezos del primer día:

  1. Cada id es único en la página y se escribe igual en los dos lados: "hora" en la interfaz es input$hora en el servidor. Un error de tipeo no avisa; el gráfico simplemente no aparece.
  2. input no se escribe. input$hora <- 9 da error. Para cambiar el valor de un control desde el servidor existen funciones como updateSliderInput(), que verás en el capítulo 12.
  3. Lo que no va dentro de server se ejecuta una sola vez al arrancar, y lo comparten todas las sesiones. Por eso leer los datos va arriba, fuera del servidor: el archivo se lee una vez y no una por visitante.

¿Qué pasa por la red cuando alguien abre la aplicación? Primero una petición normal de una página web por HTTP (Hypertext Transfer Protocol, protocolo de transferencia de hipertexto): el navegador pide la dirección y el servidor responde con el HTML de la interfaz y el archivo shiny.js. Después shiny.js abre un WebSocket (enchufe web), una conexión que queda abierta en los dos sentidos. Por ahí viajan, como mensajes cortos en JSON (JavaScript Object Notation, notación de objetos de JavaScript), los valores de las entradas hacia el servidor y las salidas ya calculadas hacia el navegador.

Este diseño explica dos cosas que vas a notar enseguida. La primera: la aplicación responde rápido aunque la página no se recargue, porque por el WebSocket viaja muy poco. La segunda: si el servidor está ocupado con un cálculo largo, la página se pone gris y espera, porque cada sesión corre en un proceso de R que hace una cosa a la vez. El capítulo 12 trata ese problema con caché y tareas asíncronas.

Entradas: deslizadores, listas, fechas y archivos

Una entrada (input) es un control que la persona usa y cuyo valor llega al servidor. Todas se crean con una función que termina en Input (o parecida) y comparten los dos primeros argumentos: el id (inputId) y la etiqueta que se ve (label). El resto depende del control.

La columna de la derecha es la que más importa, porque es donde aparecen los errores. Una lista desplegable siempre devuelve texto, aunque sus opciones parezcan números: si las opciones son los meses 1:12, el servidor recibe "7" y hay que convertirlo. Una caja numérica vacía devuelve NA, no cero. Una lista múltiple sin nada elegido devuelve NULL, y v[v$barrio %in% NULL, ] deja la tabla vacía sin avisar. Las fechas, en cambio, llegan ya como Date y se comparan directo con una columna de fechas.

Imagínalo así

Las entradas son como los formularios de una oficina. Un formulario con casillas «sí» o «no» devuelve una cruz; uno con «marque todas las que correspondan» puede volver con varias o con ninguna; una línea en blanco para escribir puede volver vacía. Quien procesa el formulario tiene que saber qué forma tiene cada respuesta antes de usarla. En Shiny, quien procesa es el servidor.

Una costumbre útil es separar lo que ve la persona de lo que recibe el código. En selectInput() y radioButtons(), un vector con nombres hace las dos cosas: choices = c("Abonados" = "abonado", "Ocasionales" = "ocasional") muestra «Abonados» y entrega "abonado", que es como está escrito en la columna usuario después de la limpieza. La interfaz habla como la gente y el código como los datos.

Salidas: gráficos, tablas y texto
Una salida (output) se declara en dos lugares que trabajan en pareja. En la interfaz, una función *Output() reserva el hueco; en el servidor, la función render*() correspondiente llena output$id con el código que produce el contenido.
En la interfazEn el servidorQué produce
plotOutput("g")output$g <- renderPlot({ … })Un gráfico de R base o de ggplot2, enviado como imagen
tableOutput("t")output$t <- renderTable({ … })Una tabla HTML simple a partir de un data frame
textOutput("x")output$x <- renderText({ … })Texto corto dentro de la página
verbatimTextOutput("p")output$p <- renderPrint({ … })Lo que R imprimiría en la consola, en monoespaciado
uiOutput("u")output$u <- renderUI({ … })Más interfaz, armada en el servidor (capítulo 12)
Cada render*() hace dos trabajos. Primero corre tu bloque de código, que puede tener muchas líneas, y se queda con el último valor. Después lo convierte en algo que el navegador entiende: renderPlot() abre un dispositivo gráfico del tamaño exacto del hueco, dibuja y manda un PNG; renderTable() convierte el data frame en HTML; renderText() pega el resultado como texto. Por eso dentro de renderPlot() se dibuja (con barplot() o devolviendo un ggplot) y no se guarda ningún archivo.
Los htmlwidgets del capítulo 08 traen su propia pareja: plotly::plotlyOutput() con renderPlotly(), leaflet::leafletOutput() con renderLeaflet(), DT::DTOutput() con DT::renderDT(). Se usan igual, y dentro de Shiny ganan algo que fuera no tenían: lo que la persona hace en el widget (un clic en el mapa, una fila elegida en la tabla) vuelve al servidor como una entrada más.

Una aplicación de los viajes que corre en la página con Shinylive
La aplicación lee la muestra de 496 viajes, la limpia con la regla del curso (quedan 486) y muestra cuántos viajes hay, su duración mediana, los viajes por hora de salida y las estaciones con más salidas. Ábrela, mueve el deslizador de la hora y cambia el barrio: todo se rehace sin que la página se recargue. Debajo del botón puedes leer el código completo.


Ver el código de app.R
library(shiny)
library(bslib, warn.conflicts = FALSE)

source("limpiar.R")
estaciones <- read.csv("estaciones.csv")
viajes <- limpiar(read.csv("viajes.csv", na.strings = ""))
viajes$hora <- as.integer(format(viajes$inicio, "%H"))
viajes$barrio <- estaciones$barrio[match(viajes$estacion_origen, estaciones$estacion_id)]

ui <- page_sidebar(
  fillable = FALSE,
  title = "Viajes de RiberaBici (muestra)",
  sidebar = sidebar(
    sliderInput("horas", "Hora de salida", min = 6, max = 23,
                value = c(6, 23), step = 1),
    selectInput("barrio", "Barrio de origen",
                choices = c("Todos", sort(unique(estaciones$barrio)))),
    radioButtons("usuario", "Usuarios",
                 choices = c("Todos" = "todos", "Abonados" = "abonado",
                             "Ocasionales" = "ocasional"))
  ),
  layout_columns(
    value_box("Viajes", textOutput("n_viajes")),
    value_box("Duración mediana", textOutput("mediana"))
  ),
  card(card_header("Viajes por hora de salida"), plotOutput("por_hora")),
  card(card_header("Estaciones con más salidas"), tableOutput("top"))
)

server <- function(input, output) {
  elegidos <- function() {
    v <- viajes[viajes$hora >= input$horas[1] & viajes$hora <= input$horas[2], ]
    if (input$barrio != "Todos") v <- v[v$barrio == input$barrio, ]
    if (input$usuario != "todos") v <- v[v$usuario == input$usuario, ]
    v
  }
  output$n_viajes <- renderText(nrow(elegidos()))
  output$mediana <- renderText({
    v <- elegidos()
    if (nrow(v) == 0) "sin viajes"
    else paste(format(round(median(v$duracion_min), 2), decimal.mark = ","), "min")
  })
  output$por_hora <- renderPlot({
    conteo <- table(factor(elegidos()$hora, levels = 6:23))
    barplot(conteo, col = "#7a3fc4", border = NA, las = 1,
            xlab = "Hora de salida", ylab = "Viajes")
  })
  output$top <- renderTable({
    v <- elegidos()
    t <- head(sort(table(v$estacion_origen), decreasing = TRUE), 5)
    data.frame(Estación = estaciones$nombre[match(names(t), estaciones$estacion_id)],
               Salidas = as.integer(t))
  })
}

shinyApp(ui, server)

# La regla de limpieza de los viajes válidos (capítulos 04 y 05), en R base
limpiar <- function(v) {
  v <- v[!duplicated(v), ]                       # duplicados exactos
  v <- v[v$estacion_origen != "E99", ]           # movimientos del taller
  v <- v[!is.na(v$fin), ]                        # bicis sin devolver
  v$inicio <- as.POSIXct(v$inicio, tz = "UTC")
  v$fin <- as.POSIXct(v$fin, tz = "UTC")
  r <- v$estacion_destino == "E17" & v$estacion_origen != "E17" &
    v$inicio >= as.POSIXct("2026-05-04", tz = "UTC") &
    v$inicio < as.POSIXct("2026-05-18", tz = "UTC")
  v$fin[r] <- v$fin[r] + 3600                    # el reloj atrasado de E17
  v$usuario <- tolower(trimws(v$usuario))
  v$duracion_min <- as.numeric(difftime(v$fin, v$inicio, units = "mins"))
  v <- v[v$duracion_min >= 1 & v$duracion_min <= 720, ]
  v$anio_nacimiento[v$anio_nacimiento == 1900] <- NA
  v
}

Diseño de la página con bslib
fluidPage() pone los controles uno debajo del otro. Para una herramienta que Ernesto use todos los días hace falta orden: los filtros a un costado, los números grandes arriba, cada gráfico en su recuadro, colores que no parezcan de prueba. Eso lo da bslib, el paquete de Posit que lleva a Shiny las piezas de Bootstrap (el sistema de diseño web más usado para páginas que se acomodan a la pantalla) en su versión 5.
Imagínalo así
Armar una página con bslib es como amoblar una casa con muebles modulares. No fabricas cada repisa: eliges un armazón (una casa con barra lateral, una con pestañas), colocas módulos estándar (tarjetas, cajas de valor, columnas) y al final pintas todo de un color. Los módulos encajan entre sí y se reacomodan solos cuando cambias de pieza, que aquí es cambiar de la pantalla grande al celular.
Las piezas que vas a usar casi siempre:
  • page_sidebar(): una página con título arriba y una barra lateral (sidebar) para los controles. En el celular, la barra se pliega detrás de un botón. Para aplicaciones con varias vistas está page_navbar(), con una barra de navegación (navbar) y una pestaña por vista.
  • card(): una tarjeta (card), un recuadro con borde que agrupa una salida y su título (card_header()). Puede crecer a pantalla completa con un clic si le pasas full_screen = TRUE.
  • value_box(): una caja de valor (value box) para un número grande con su etiqueta: viajes, duración mediana, estaciones vacías.
  • layout_columns(): reparte lo que contiene en columnas que se apilan cuando no caben.
  • bs_theme(): el tema (theme) de toda la página. bs_theme(primary = "#7a3fc4") cambia el color principal; bs_theme(bootswatch = "minty") aplica uno de los temas listos de Bootswatch; base_font = font_google("Inter") cambia la fuente.
Un detalle que conviene saber pronto: por omisión page_sidebar() hace que el contenido llene el alto de la ventana y reparte ese alto entre las tarjetas. Con dos o tres tarjetas queda bien; con más, cada gráfico queda aplastado. page_sidebar(fillable = FALSE) devuelve el comportamiento de una página normal, que crece hacia abajo y se recorre con la rueda del ratón.

# ~/bicis/app-viajes/app.R
library(shiny)
library(bslib)

source("limpiar.R")
estaciones <- read.csv("../datos/estaciones.csv")
viajes <- limpiar(read.csv("../datos/viajes.csv", na.strings = ""))
viajes$hora <- as.integer(format(viajes$inicio, "%H"))
viajes$barrio <- estaciones$barrio[match(viajes$estacion_origen,
                                         estaciones$estacion_id)]

ui <- page_sidebar(
  title = "Viajes de RiberaBici",
  theme = bs_theme(primary = "#7a3fc4"),
  sidebar = sidebar(
    sliderInput("horas", "Hora de salida", min = 6, max = 23,
                value = c(6, 23), step = 1),
    selectInput("barrio", "Barrio de origen",
                choices = c("Todos", sort(unique(estaciones$barrio)))),
    dateRangeInput("fechas", "Período", start = "2026-03-01",
                   end = "2026-08-31", language = "es", separator = "a")
  ),
  layout_columns(
    value_box("Viajes", textOutput("n_viajes")),
    value_box("Duración mediana", textOutput("mediana"))
  ),
  card(card_header("Viajes por hora de salida"), plotOutput("por_hora"))
)

server <- function(input, output) {
  elegidos <- function() {
    dia <- as.Date(viajes$inicio)
    v <- viajes[viajes$hora >= input$horas[1] & viajes$hora <= input$horas[2] &
                  dia >= input$fechas[1] & dia <= input$fechas[2], ]
    if (input$barrio != "Todos") v <- v[v$barrio == input$barrio, ]
    v
  }
  output$n_viajes <- renderText(format(nrow(elegidos()), big.mark = ".",
                                             decimal.mark = ","))
  output$mediana <- renderText({
    m <- median(elegidos()$duracion_min)
    paste(format(round(m, 2), decimal.mark = ","), "min")
  })
  output$por_hora <- renderPlot({
    barplot(table(factor(elegidos()$hora, levels = 6:23)),
            col = "#7a3fc4", border = NA, las = 1,
            xlab = "Hora de salida", ylab = "Viajes")
  })
}

Shiny para Python: la misma idea en otro lenguaje
Desde 2022 existe Shiny para Python (Shiny for Python), también de Posit. No es una traducción línea por línea sino la misma arquitectura: una interfaz declarada, un servidor que responde, el mismo WebSocket y el mismo modelo reactivo que verás en el capítulo 11. Las funciones de bslib están incluidas desde el principio con nombres casi iguales (ui.page_sidebar, ui.card, ui.value_box).
Cambian tres cosas de forma, todas propias de Python. Las entradas se leen llamándolas: input.horas() en lugar de input$horas. Las salidas no se asignan a una lista: se escribe una función con el nombre del id y se la marca con un decorador (decorator), una línea con @ arriba de la función, como @render.plot. Y el gráfico lo dibuja matplotlib (u otra biblioteca de Python) en lugar de R.
# R
output$n_viajes <- renderText(nrow(elegidos()))

# Python
@render.text
def n_viajes():
    return len(elegidos())
Hay además un modo abreviado, Shiny Express, donde la interfaz y el servidor se mezclan en un solo guion. Es cómodo para prototipos; para aplicaciones que crecen, la forma con App(app_ui, server) se parece más a la de R y se ordena mejor. ¿Cuál conviene? Si el análisis ya está en R (modelos, gráficos de ggplot2, paquetes de CRAN), Shiny para R; si el equipo y sus bibliotecas viven en Python, Shiny para Python, sin cambiar de modelo mental. El lenguaje en sí está en Programación en Python.

# ~/bicis/app-py/app.py: la misma idea en Shiny para Python
import pandas as pd
import matplotlib.pyplot as plt
from shiny import App, render, ui

viajes = pd.read_csv("../datos/viajes.csv", parse_dates=["inicio", "fin"])
viajes = viajes.drop_duplicates()
viajes = viajes[(viajes["estacion_origen"] != "E99") & viajes["fin"].notna()].copy()
reloj = ((viajes["estacion_destino"] == "E17") & (viajes["estacion_origen"] != "E17")
         & viajes["inicio"].between("2026-05-04", "2026-05-17 23:59:59"))
viajes.loc[reloj, "fin"] += pd.Timedelta(hours=1)
viajes["duracion_min"] = (viajes["fin"] - viajes["inicio"]).dt.total_seconds() / 60
viajes = viajes[viajes["duracion_min"].between(1, 720)]
viajes["hora"] = viajes["inicio"].dt.hour

app_ui = ui.page_sidebar(
    ui.sidebar(
        ui.input_slider("horas", "Hora de salida", min=6, max=23, value=(6, 23)),
    ),
    ui.value_box("Viajes", ui.output_text("n_viajes")),
    ui.card(ui.card_header("Viajes por hora de salida"), ui.output_plot("por_hora")),
    title="Viajes de RiberaBici (Python)",
)

def server(input, output, session):
    def elegidos():
        desde, hasta = input.horas()
        return viajes[viajes["hora"].between(desde, hasta)]

    @render.text
    def n_viajes():
        return f"{len(elegidos()):,}".replace(",", ".")

    @render.plot
    def por_hora():
        conteo = elegidos()["hora"].value_counts().sort_index()
        fig, ax = plt.subplots()
        ax.bar(conteo.index, conteo.values, color="#7a3fc4")
        ax.set_xlabel("Hora de salida")
        ax.set_ylabel("Viajes")
        return fig

app = App(app_ui, server)

shiny run --reload app.py

Compara los dos archivos: ui.page_sidebar frente a page_sidebar, input.horas() frente a input$horas, @render.text frente a output$n_viajes <- renderText(). La forma cambia; la arquitectura (interfaz, servidor, ids que los unen) es idéntica.


La idea clave
Una aplicación Shiny son dos declaraciones y un cable. La interfaz dice qué se ve: entradas con un id y huecos de salida con otro. El servidor dice cómo se calcula cada salida a partir de input. El id une las dos partes, y Shiny se encarga de la red: un WebSocket que lleva cada cambio y trae cada resultado, sin recargar la página. Con bslib la página toma forma de herramienta (barra lateral, tarjetas, cajas de valor, un tema), y la misma idea existe en Python. Lo que todavía no sabes es cómo decide Shiny qué volver a calcular: eso es la reactividad, el capítulo siguiente.


Pruébate
Pruébate
¿Qué diferencia hay entre ui y server en una aplicación Shiny?
ui es un objeto que describe la página (se convierte en HTML una vez); server es una función que Shiny llama una vez por sesión y que contiene el código que calcula cada salida a partir de input.
Escribiste plotOutput("grafico") en la interfaz y output$grafica <- renderPlot(...) en el servidor. ¿Qué pasa?
El hueco del gráfico queda vacío y no aparece ningún error: los ids no coinciden, así que Shiny no sabe que esa salida va en ese hueco.
¿Por qué conviene leer el archivo de viajes fuera de la función server?
Porque lo que está fuera se ejecuta una sola vez al arrancar y lo comparten todas las sesiones; dentro del servidor, se leería una vez por cada persona que abra la aplicación.
Una selectInput() tiene como opciones los números del 1 al 12. ¿Qué tipo de valor recibe el servidor?
Texto, por ejemplo "7". Las listas desplegables siempre devuelven texto; hay que convertirlo con as.integer() antes de comparar con una columna numérica.
¿Qué viaja por el WebSocket cuando la persona mueve un deslizador?
Solo el valor nuevo de esa entrada, como un mensaje JSON corto. De vuelta viajan solo las salidas que dependen de ella, ya calculadas (un gráfico como imagen, un texto).
¿En qué caso no conviene publicar con Shinylive?
Cuando los datos son confidenciales o muy grandes: con Shinylive la aplicación y sus datos se descargan al navegador de cada visitante. También si necesita paquetes que no existen para webR o conectarse a una base de datos interna.
