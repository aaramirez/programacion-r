Funciones, entornos y programación funcional

Gabriela ya copió y pegó el mismo bloque de limpieza tres veces, y cada copia quedó un poco distinta. Este capítulo convierte ese bloque en una función, explica dónde busca R cada nombre que usas y enseña a aplicar una función a una lista completa sin escribir un bucle.

Definir funciones: argumentos, valores por defecto y ...

El primer lunes de cada mes, Ernesto Salas le pide a Gabriela Rondón lo mismo: cuántos viajes válidos hubo, cuánto duró el viaje típico y cómo se repartieron entre abonados y ocasionales. Gabriela tiene el código de los capítulos anteriores: leer viajes.csv, quitar duplicados, sacar el taller E99, corregir el reloj de E17, normalizar el tipo de usuario, calcular la duración y descartar los re-anclajes y las bicis olvidadas. Son quince líneas. En abril las copió en otro guion para revisar solo los abonados; en mayo, en otro para las eléctricas. En junio Ignacio Peña le avisó que el reloj de E17 se había atrasado otra vez, y Gabriela tuvo que buscar y corregir las tres copias. Se le escapó una.

Ese es el momento de escribir una función (function): darle un nombre a un bloque de código para usarlo cuantas veces quieras, con datos distintos, y corregirlo en un solo lugar.

Imagínalo así

Una función es una receta escrita en una tarjeta. La receta de la salsa dice qué ingredientes recibe (tomates, sal, y un «al gusto» para el ají), qué pasos seguir y qué entrega al final. No hace falta reescribir los pasos cada vez que cocinas: tomas la tarjeta, le das los ingredientes de hoy y obtienes la salsa. Si un día descubres que convenía menos sal, corriges la tarjeta y todas las salsas futuras salen bien.

En R una función se crea con la palabra function y se guarda con un nombre, como cualquier otro valor:

duracion_min <- function(inicio, fin, unidad = "mins") {
  d <- as.numeric(difftime(fin, inicio, units = unidad))
  d[d < 0] <- NA
  round(d, 1)
}

Entre paréntesis van los argumentos (arguments): los ingredientes. unidad = "mins" es un valor por defecto (default value): si quien llama no dice nada, vale "mins". Entre llaves va el cuerpo (body). La función devuelve el valor de la última expresión evaluada, aquí round(d, 1); no hace falta escribir return(), que se reserva para salir antes de tiempo («si no hay datos, devuelve NA y no sigas»).

Tres cosas de las funciones de R sorprenden a quien viene de otros lenguajes. La primera: una función no tiene nombre propio. duracion_min es una variable que guarda una función, igual que limite <- 30 guarda un número. Puedes guardarla en una lista, pasarla a otra función o no darle nombre nunca.

La segunda: los argumentos se pueden dar por nombre o por posición, y R los empareja en este orden: primero los nombres exactos, después los nombres abreviados (un uni = "hours" alcanzaría para unidad, aunque es mala costumbre) y al final, por posición, los que quedan. Por eso duracion_min(fin = f, inicio = i) y duracion_min(i, f) dan lo mismo. La convención de la comunidad: los datos van primero y sin nombre; las opciones, después y con nombre.

La tercera es el argumento ... (se lee «punto punto punto», en inglés dots): recoge cualquier cantidad de argumentos extra y los pasa a otra función sin tocarlos. Es lo que permite que mean(x, na.rm = TRUE) acepte opciones que solo conoce mean:

mediana_por <- function(x, grupo, ...) {
  tapply(x, grupo, median, ...)
}
mediana_por(validos$duracion_min, validos$usuario, na.rm = TRUE)

na.rm = TRUE entra por ... y llega intacto a median. Con ... también se escriben funciones como paste() o c(), que aceptan tantos valores como les des.

Para validar los argumentos al entrar, R base trae dos ayudas. match.arg() acepta solo valores de una lista (unidad = c("mins", "hours") y luego unidad <- match.arg(unidad): si alguien escribe "minutos", falla con un mensaje claro). stopifnot() revisa condiciones: stopifnot(inherits(inicio, "POSIXct")) se detiene si inicio todavía es texto.

Con esto, el bloque de quince líneas de Gabriela se vuelve una función. La guarda en su propio archivo, limpiar.R, para que cualquier guion la cargue con source("limpiar.R"):

# limpiar.R: la regla de los viajes válidos de RiberaBici (capítulo 04)
limpiar_viajes <- function(v, desde = "2026-05-04", hasta = "2026-05-18") {
  v <- v[!duplicated(v), ]                     # filas repetidas
  v <- v[v$estacion_origen != "E99", ]         # movimientos del taller
  v <- v[!is.na(v$fin), ]                      # bicis sin devolver
  v$inicio <- as.POSIXct(v$inicio, tz = "UTC")
  v$fin <- as.POSIXct(v$fin, tz = "UTC")
  atrasado <- v$estacion_destino == "E17" & v$estacion_origen != "E17" &
    v$inicio >= as.POSIXct(desde, tz = "UTC") & v$inicio < as.POSIXct(hasta, tz = "UTC")
  v$fin[atrasado] <- v$fin[atrasado] + 3600    # el reloj de E17
  v$usuario <- tolower(trimws(v$usuario))
  v$duracion_min <- as.numeric(difftime(v$fin, v$inicio, units = "mins"))
  v <- v[v$duracion_min >= 1 & v$duracion_min <= 720, ]
  v$anio_nacimiento[v$anio_nacimiento %in% 1900] <- NA
  v
}

Las fechas del reloj atrasado son argumentos con valor por defecto: si Ignacio avisa de otro atraso, se llama a la función con otras fechas y no se toca el código. Las horas se leen en UTC porque la ciudad no cambia la hora en verano: así no hay que pelear con zonas horarias.

Control de flujo: if, for, while y switch

Dentro de una función, a veces hay que decidir o repetir. R tiene las estructuras de siempre, con dos detalles propios.

if (condición) { … } else { … } decide según un solo valor lógico. Si le das un vector de largo mayor que uno, R se detiene con el error the condition has length > 1 (desde R 4.2; antes solo avisaba y usaba el primer elemento, una fuente clásica de errores silenciosos). Para decidir elemento por elemento se usa la versión vectorizada, ifelse(test, si, no), o dplyr::if_else(), que además revisa los tipos:

etiqueta <- ifelse(validos$duracion_min > 30, "larga", "corta")
if (nrow(validos) == 0) stop("no quedó ningún viaje válido")

if también devuelve un valor, así que se puede asignar: unidad <- if (horas) "hours" else "mins".

for (x in vector) { … } recorre un vector o una lista. Para recorrer por posición, usa seq_along(x) y no 1:length(x): si x está vacío, 1:length(x) es 1:0, que vale c(1, 0), y el bucle corre dos veces sobre nada. while (condición) { … } repite mientras la condición sea cierta; repeat { … } repite hasta un break, y next salta a la vuelta siguiente.

switch(valor, opcion1 = …, opcion2 = …) elige entre varias ramas por un texto, más limpio que una escalera de if:

descripcion <- function(usuario) {
  switch(usuario,
    abonado = "pase anual",
    ocasional = "pase por viaje o por día",
    personal = "taller y mantenimiento",
    stop("tipo de usuario desconocido: ", usuario))
}
descripcion("ocasional")

La última opción, sin nombre, es la que se usa si ninguna coincide.

¿Cuándo es el bucle la herramienta correcta? Cuando cada paso depende del anterior. Si Cecilia quiere saber cuántas bicis quedan en E06 después de cada salida y cada llegada de la mañana, el estado de las 8:05 depende del de las 8:04: no hay operación vectorizada que lo resuelva de una vez, y un for que recorre los eventos en orden es lo natural (en el capítulo 06 lo vas a escribir con un objeto que cambia). Lo mismo vale para una simulación o un proceso que espera hasta que algo ocurra.

Un consejo que vale por todo el capítulo: en R, antes de escribir un bucle, pregúntate si la operación ya es vectorizada (capítulo 02). validos$duracion_min * 60 pasa todas las duraciones a segundos sin un for. Y si el bucle es inevitable, reserva el espacio antes: un vector que crece con x <- c(x, nuevo) se copia completo en cada vuelta. En la práctica de más abajo vas a medir la diferencia: con 20.000 elementos, el vector que crece tarda decenas de veces más que el reservado con numeric(n).

Entornos y alcance léxico

Dentro de limpiar_viajes aparecen nombres que no son argumentos: duplicated, as.POSIXct, difftime. Y en otros ejemplos aparecerán variables que la función usa sin que nadie se las pase. ¿Dónde las busca R?

La respuesta está en los entornos (environments). Un entorno es una bolsa de nombres, cada uno con su valor, más una referencia a otro entorno, su padre (parent). Cuando R necesita el valor de un nombre, lo busca en el entorno actual; si no está, sube al padre, y así hasta encontrarlo o llegar al entorno vacío (empty environment), donde se rinde con object not found.

Imagínalo así

Piensa en una familia que vive en varias casas, cada una con un papel pegado en la puerta que dice dónde vive la abuela. Si necesitas una escalera, la buscas primero en tu casa; si no está, vas a la casa de la dirección del papel; si tampoco, sigues el papel de esa casa. Nunca buscas en la casa del vecino que te pidió el favor: solo sigues los papeles. El último papel dice «no hay más casas», y ahí aceptas que la escalera no existe.

Lo que escribes en la consola vive en el entorno global (global environment, R_GlobalEnv). Debajo de él está la ruta de búsqueda (search path): un entorno por cada paquete cargado, que search() lista en orden, desde package:stats hasta package:base. library(purrr) mete un entorno nuevo justo debajo del global. Por eso mean funciona sin que la definas: R baja hasta package:base y la encuentra. Y por eso, si creas un objeto llamado mean en el global, lo encontrará antes y lo tapará. El operador :: evita la búsqueda: stats::sd(x) va directo al paquete.

Cada vez que llamas a una función, R crea un entorno nuevo, el entorno de ejecución (execution environment), donde viven los argumentos y las variables que la función crea. Al terminar se descarta: por eso las variables de una función no ensucian el global. La pregunta importante es quién es su padre. En R, el padre del entorno de ejecución es el entorno donde se escribió la función, no el de quien la llama. Eso se llama alcance léxico (lexical scoping): basta leer el código para saber dónde se buscará cada nombre.

Evaluación perezosa de los argumentos
R no evalúa los argumentos al llamar a la función, sino la primera vez que el cuerpo los usa. Esto se llama evaluación perezosa (lazy evaluation), y cada argumento todavía no evaluado es una promesa (promise): una nota con la expresión y el entorno donde calcularla.
Imagínalo así
En una cafetería pides un café y un sándwich «si después tengo hambre». El mesero anota los dos, pero el sándwich solo se prepara si lo llamas. Si nunca lo pides, la cocina nunca se entera, aunque te hayas equivocado al nombrar el relleno. Una promesa de R es esa nota: la expresión espera anotada hasta que alguien la necesite.
Tres consecuencias prácticas:
f <- function(x, y) {
  x * 2
}
f(10, stop("esto nunca se evalúa"))    # 20: y no se usó

resumen <- function(x, n = length(x)) {
  x <- x[!is.na(x)]
  c(n = n, media = mean(x))
}
resumen(c(12, NA, 18))
La primera llamada devuelve 20 sin error, porque y nunca se usó. La segunda muestra que un valor por defecto puede depender de otros argumentos, porque se evalúa dentro de la función. Y tiene una trampa: n vale 2, no 3, porque length(x) se calculó recién cuando c(n = n, …) lo pidió, después de quitar el NA. Si quieres fijar un argumento al entrar, usa force(n) en la primera línea.
La evaluación perezosa parece un detalle, pero es la base de dos cosas grandes del curso. Como la función recibe la expresión antes de evaluarla, puede decidir dónde evaluarla: así dplyr::filter(viajes, duracion_min > 30) entiende que duracion_min es una columna (capítulo 05). Y el grafo reactivo de Shiny (capítulo 11) usa la misma idea: no se calcula nada hasta que alguien lo pide.


Funciones como valores y clausuras
Si una función es un valor, se puede hacer con ella todo lo que se hace con un número: guardarla en una lista, pasarla como argumento o devolverla desde otra función. A ese estilo se le llama programación funcional (functional programming), y R lo heredó de Scheme.
Pasar una función como argumento ya lo hiciste: en tapply(x, grupo, median), median va sin paréntesis porque se entrega la función, no su resultado. Una función que se escribe donde se usa, sin nombre, es una función anónima (anonymous function): function(x) mean(x > 30) o, desde R 4.1, su forma corta \(x) mean(x > 30).
resumenes <- list(mediana = median, media = mean, p90 = \(x) quantile(x, 0.9))
sapply(resumenes, \(f) f(validos$duracion_min))
Una lista de tres funciones, aplicadas una por una al mismo vector. Con los datos completos sale mediana 18,65, media 20,58 y percentil 90 de 35,38 minutos.
Lo contrario también vale: una función puede devolver otra. Se le dice fábrica de funciones (function factory):
crear_filtro <- function(limite) {
  function(minutos) minutos > limite
}
largo45 <- crear_filtro(45)
largo45(c(30, 50))
largo45 recuerda que limite vale 45 aunque crear_filtro ya terminó. ¿Cómo? La función de adentro nació en el entorno de ejecución de crear_filtro; ese entorno es su padre, y como largo45 lo sigue necesitando, R no lo descarta. Una función más el entorno que recuerda es una clausura (closure). En R, técnicamente, todas las funciones que escribes son clausuras: por eso typeof(mean) dice "closure". El ejemplo 3 del laboratorio de entornos muestra la clausura por dentro.
R base trae tres funciones clásicas de la programación funcional: Filter(f, x) se queda con los elementos donde f da TRUE, Map(f, x, y) aplica f a pares de elementos y Reduce(f, x) combina todos los elementos de a dos (Reduce("+", 1:4) es ((1 + 2) + 3) + 4). Las verás poco, porque purrr tiene versiones más consistentes, pero el patrón aparece en todas partes.


La familia apply y purrr: map en lugar de bucles
El pedido de Ernesto vuelve con una variante: «la mediana de duración, pero mes por mes». Con un bucle hay que crear el vector, recorrer los meses con un índice y llenar cada posición. La alternativa funcional dice lo mismo en una línea: aplica esta función a cada elemento de esta lista.
Imagínalo así
Un sello de fechar. Pones la pila de facturas al lado, tomas el sello y lo aplicas a cada una: no cuentas las facturas, no llevas un índice, no anotas en qué número vas. Solo dices «a cada una, esto». map es el sello: tú das la pila (la lista) y lo que hay que hacer (la función).
R base tiene la familia apply. lapply(x, f) aplica f a cada elemento de x y devuelve una lista del mismo largo; sapply intenta simplificar el resultado a un vector o una matriz; vapply exige que declares el tipo de cada resultado; apply recorre filas o columnas de una matriz, y tapply aplica por grupos. El paquete purrr, parte del tidyverse, tiene la misma idea con nombres que dicen qué devuelven: map() devuelve siempre una lista; map_dbl(), map_int(), map_chr() y map_lgl(), un vector del tipo indicado o un error; map2() recorre dos listas a la vez, e imap() pasa también el nombre o la posición de cada elemento.
¿Cuál usar? sapply es cómoda en la consola, pero su resultado depende de los datos: si la función devuelve un número, da un vector; si devuelve dos, una matriz; si la lista viene vacía, una lista vacía. Dentro de una función que otros van a usar, prefiere vapply o map_dbl, que fallan cuando la forma no es la esperada. El laboratorio muestra los tres estilos con el mismo cálculo, incluido el caso en que sapply sorprende.

Como un data frame es una lista de columnas (capítulo 03), estas funciones también lo recorren columna por columna: sapply(viajes, class) dice el tipo de cada columna en una línea. Para recorrer una tabla por grupos, el patrón es partir con split() y aplicar: split(validos, validos$usuario) da una lista de dos tablas, y map(…, \(d) median(d$duracion_min)) resume cada una. Para el caso inverso, juntar muchas tablas en una (por ejemplo, un archivo por mes), map() lee cada una y purrr::list_rbind() las apila. Errores, advertencias y depuración con browser()
Una función bien escrita avisa cuando algo anda mal. R tiene tres señales, llamadas condiciones (conditions), de menos a más grave: un mensaje (message) informa y el código sigue; una advertencia (warning) avisa de algo raro y el código sigue (as.numeric("doce") da NA con el aviso NAs introduced by coercion), y un error (error) detiene la función. Las tres se emiten con message(), warning() y stop().
Un error no se queda donde nace: sube por la pila de llamadas (call stack) hasta que alguien lo atrapa. Para atraparlo está tryCatch():
r <- tryCatch(resumir_estacion(validos, "E25"),
              error = function(e) { message("Atrapado: ", conditionMessage(e)); NA })
Si la expresión falla, tryCatch la abandona y devuelve lo que diga el manejador; su argumento finally corre siempre, falle o no (sirve para cerrar una conexión o borrar un archivo temporal). withCallingHandlers() es su pariente: atiende la condición y deja que el código continúe, útil para anotar las advertencias en un registro. Y purrr tiene dos atajos para cuando aplicas una función a muchos elementos y algunos pueden fallar: possibly(f, otherwise = NA) devuelve NA en vez del error, y safely(f) devuelve el resultado y el error por separado.
Cuando el error es tuyo y no sabes dónde está, R ofrece herramientas de depuración (debugging):
  • traceback(), justo después del error, muestra la pila: qué función llamó a cuál hasta llegar a la que falló.
  • browser(), escrito dentro de una función, la detiene en esa línea y te deja en una consola dentro de su entorno de ejecución: puedes mirar los argumentos y las variables, ejecutar líneas y avanzar con n (siguiente), c (continuar) o Q (salir).
  • debugonce(f) hace lo mismo desde el principio de f en la próxima llamada, sin editar el código. RStudio y Positron permiten además poner un punto de interrupción (breakpoint) con un clic al lado del número de línea.

Vas a provocar un error a propósito, atraparlo de tres formas y entrar a una función con el depurador. Necesitas limpiar.R y purrr de las prácticas anteriores.

library(purrr)

  if (nrow(d) == 0) stop("no hay viajes desde ", estacion)
  c(salidas = nrow(d), mediana = median(d$duracion_min))

              error = function(e) { message("Atrapado: ", conditionMessage(e)); NA })

  2. Escribe debugonce(resumir_estacion) y luego resumir_estacion(validos, "E06"). Ya dentro, escribe estacion, pulsa n dos veces, escribe nrow(d) y termina con c.

Un caso real
El estilo funcional que llegó a R base. Durante años, la forma corta de escribir funciones anónimas y la tubería vivían en paquetes. En mayo de 2021, R 4.1.0 incorporó a R base las dos cosas: la sintaxis \(x) y la tubería |>. El equipo central de R, que cambia el lenguaje con mucha cautela para no romper código de décadas, consideró que el estilo de funciones pequeñas encadenadas ya era la forma dominante de escribir R. Puedes leerlo en las noticias de esa versión, en el sitio de CRAN.


La idea clave
En R, una función es un valor como cualquier otro: se guarda con un nombre, se pasa a otras funciones y se devuelve desde ellas. Cada llamada crea un entorno de ejecución cuyo padre es el lugar donde la función se escribió (alcance léxico), y R busca cada nombre subiendo por esa cadena hasta el entorno vacío. Los argumentos se evalúan solo cuando se usan, lo que permite a dplyr y a Shiny leer el código antes de ejecutarlo. Con funciones pequeñas que reciben todo lo que usan, y con map para aplicarlas a listas completas, el código de Gabriela dejó de copiarse: se corrige en un solo lugar y se reutiliza.


Pruébate
Pruébate
¿Qué devuelve una función de R si no tiene return()?
El valor de la última expresión evaluada en su cuerpo. return() se usa para salir antes de llegar al final.
Si una función usa una variable que no es argumento ni se crea adentro, ¿dónde la busca R?
En el entorno donde se escribió la función (su entorno de encierro) y, si no está, en los padres de ese entorno: el global, los paquetes de la ruta de búsqueda y package:base. Nunca en el entorno de quien la llamó.
¿Por qué f(10, stop("error")) puede no dar error?
Por la evaluación perezosa: si f nunca usa su segundo argumento, la promesa no se evalúa y el stop no se ejecuta.
¿Qué es una clausura?
Una función junto con el entorno donde fue creada, que sigue existiendo mientras la función lo necesite. Permite que una función devuelta por una fábrica recuerde los valores de la llamada que la creó.
¿Por qué conviene vapply o map_dbl en lugar de sapply dentro de una función?
Porque declaran el tipo y la forma del resultado y fallan si no se cumplen; sapply devuelve un vector, una matriz o una lista según los datos, y el error aparece más tarde y en otro lugar.
¿Qué diferencia hay entre tryCatch y withCallingHandlers?
tryCatch atrapa la condición y abandona la expresión, devolviendo lo que diga el manejador; withCallingHandlers ejecuta el manejador y deja que la expresión siga.
