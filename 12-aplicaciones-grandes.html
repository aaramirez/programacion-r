Aplicaciones grandes: módulos, estado y rendimiento

La aplicación de Gabriela ya tiene seiscientas líneas en un solo archivo y Ernesto quiere ver tres estaciones lado a lado. Este capítulo enseña a partirla en módulos con su propio espacio de nombres, a validar lo que entra, a subir y descargar archivos, a no calcular dos veces lo mismo y a ordenar el proyecto para que pueda seguir creciendo.

Gabriela Rondón abrió su app.R un lunes y tuvo que bajar hasta la línea 612 para encontrar el gráfico que quería cambiar. La aplicación de los viajes había empezado en el capítulo 10 con tres filtros y un gráfico por hora; ahora tenía también el tipo de usuario, una tabla, un mapa, la búsqueda con debounce() del capítulo 11 y tres pestañas. Módulos de Shiny: espacios de nombres y comunicación entre módulos

Imagínalo así

En un edificio hay veinte apartamentos y en cada uno vive alguien que se llama «la familia». Si el cartero recibe una carta para «la familia», no sabe a qué puerta llevarla. Por eso cada carta lleva el número del apartamento delante: «3-B, la familia». Dentro del apartamento nadie se llama a sí mismo «3-B»; el número solo importa afuera, para que el cartero no se equivoque.

En una página web, cada elemento que Shiny conecta tiene un identificador (id), y el id tiene que ser único en toda la página. Cuando Gabriela copió la tarjeta, la página quedó con tres desplegables estacion: el navegador encuentra el primero y Shiny lee un solo input$estacion. Es la carta sin número de apartamento.

Un módulo de Shiny (Shiny module) resuelve eso. Es un par de funciones, una para la interfaz y otra para el servidor, que se escriben una vez y se llaman tantas veces como haga falta, cada vez con un id distinto. La pieza clave es el espacio de nombres (namespace): la función NS(id) devuelve otra función que le pega el id delante a cada nombre, con un guion. NS("lomas")("estacion") da "lomas-estacion".

tarjetaUI <- function(id, opciones, inicial) {
  ns <- NS(id)                            # ns("estacion") -> "lomas-estacion"
  wellPanel(
    selectInput(ns("estacion"), "Estación", opciones, selected = inicial),
    tableOutput(ns("cifras"))
  )
}

tarjetaServer <- function(id, totales) {
  moduleServer(id, function(input, output, session) {
    fila <- reactive({
      req(input$estacion)                 # dentro del módulo, sin prefijo
      totales[totales$estacion_id == input$estacion, ]
    })
    output$cifras <- renderTable(fila())
    fila                                  # lo que el módulo devuelve
  })
}

Dos reglas hacen que funcione. En la interfaz, todo id pasa por ns(): si uno se escapa, ese elemento vuelve a ser compartido. En el servidor, moduleServer(id, ...) hace la traducción inversa: el código escribe input$estacion y output$cifras, y Shiny los busca como lomas-estacion y lomas-cifras. El módulo no sabe cuántas veces se usa ni qué id le tocó; por eso se puede reutilizar.

En la aplicación, la interfaz y el servidor llaman al módulo con el mismo id. Si la interfaz dice tarjetaUI("lomas", ...) y el servidor tarjetaServer("lomas", ...), quedan conectados; si los ids no coinciden, la tarjeta se dibuja pero nunca responde, y Shiny no avisa.

ui <- fluidPage(
  fluidRow(
    column(4, tarjetaUI("lomas", opciones, "E10")),
    column(4, tarjetaUI("universidad", opciones, "E06")),
    column(4, tarjetaUI("puerto", opciones, "E24"))
  )
)
server <- function(input, output, session) {
  tarjetaServer("lomas", totales)
  tarjetaServer("universidad", totales)
  tarjetaServer("puerto", totales)
}

Cómo se hablan los módulos

Un tablero real no es una tarjeta repetida: es un módulo de filtros, uno de mapa, uno de gráfico y uno de tabla, y los tres últimos dependen de lo que se elige en el primero. La tentación es que el mapa lea input[["filtros-barrio"]] directamente. Funciona, pero ata el mapa al nombre interno de otro módulo: si alguien cambia el id del filtro, el mapa deja de funcionar sin que nada lo indique.

La forma que recomienda la documentación de Shiny es más simple y más segura: los datos bajan como argumentos y suben como valor de retorno. El módulo de filtros devuelve una expresión reactiva; el servidor principal la recibe y se la pasa a los demás.

server <- function(input, output, session) {
  datos <- filtrosServer("filtros", viajes)   # devuelve reactive(...)
  mapaServer("mapa", datos)                    # se pasa sin paréntesis
  horasServer("horas", datos)
}

El detalle que más errores causa está en los paréntesis. Se pasa datos, el reactivo, y dentro del módulo se lee datos(). Si se pasara datos(), el módulo recibiría el valor de ese momento y nunca se enteraría de los cambios: el mapa quedaría congelado en la primera selección.

Lo que se devuelve puede ser un reactivo o una lista de reactivos (list(datos = datos, estacion = estacion)). Lo que un módulo no debe hacer es escribir en una variable global con <<- para que otro la lea: el grafo reactivo no ve esa dependencia y la segunda pieza no se actualiza. Si dos módulos necesitan escribir sobre el mismo estado, el servidor principal crea un reactiveVal() y se lo pasa a los dos, que lo leen y lo cambian a la vista de todos.

Interfaces dinámicas: renderUI e insertUI

Hasta aquí la interfaz era fija: se declara en ui y no cambia. A veces la forma de la página depende de lo que el usuario elige. Shiny ofrece tres herramientas, de la más liviana a la más poderosa:

  • Actualizar una entrada que ya existe con las funciones update*: updateSelectInput(), updateSliderInput(). Cambian las opciones o el valor sin redibujar nada. Es lo primero que hay que probar: si al elegir un barrio solo deben cambiar las estaciones del segundo desplegable, basta con updateSelectInput().
  • renderUI() con uiOutput(): el servidor construye un trozo de interfaz con las mismas funciones de ui y lo manda a la página. Cada vez que se invalida, el trozo se reconstruye entero, y lo que el usuario había escrito o elegido adentro se pierde.
  • insertUI() y removeUI(): agregan o quitan piezas en un lugar de la página (un selector CSS, como "#extra") sin tocar lo demás. Son las que usa el botón «Agregar otra tarjeta» del laboratorio, junto con una llamada nueva a tarjetaServer() con un id nuevo.

Para mostrar u ocultar algo según una entrada, sin pasar por el servidor, existe conditionalPanel(), que evalúa una condición en JavaScript dentro del navegador.

En la práctica

Validar entradas y mostrar errores con req() y validate()

Imagínalo así

Un buen portero no deja pasar a nadie sin la entrada, pero tampoco grita: si alguien todavía no la tiene, simplemente espera. Si la entrada es falsa, explica por qué no puede pasar. Shiny tiene los dos porteros: uno que espera en silencio y otro que explica.

Cuando la aplicación arranca, input$estacion puede ser NULL por un instante; si el usuario borra todos los barrios de un filtro, la tabla queda vacía; si sube un archivo con otras columnas, el código de más abajo falla con un mensaje en inglés que nadie entiende. Validar es decidir, en cada caso, qué ve el usuario.

req() es el portero silencioso. Si su argumento es NULL, FALSE, un texto vacío o un vector de largo cero, detiene el reactivo o la salida sin mostrar error: la salida queda en blanco y se vuelve a intentar cuando la entrada cambie. Por dentro lanza un error especial, de la clase shiny.silent.error, que Shiny no muestra.

validate() con need() es el portero que explica. Si la condición es falsa, la salida muestra el mensaje en gris en lugar del gráfico, y todo lo que depende de ese reactivo también:

datos <- reactive({
  validate(need(length(input$barrios) > 0, "Elige al menos un barrio."))
  viajes[viajes$barrio %in% input$barrios, ]
})

Para avisos que no reemplazan una salida (un archivo guardado, un proceso que tardará), showNotification() muestra un recuadro temporal en una esquina. Y si un cálculo puede fallar por causas externas, tryCatch() atrapa el error y lo convierte en un mensaje propio. Una regla de seguridad: en un servidor, Shiny oculta el texto de los errores de R con la opción shiny.sanitize.errors, para no revelar rutas ni detalles internos; si quieres que el usuario vea un mensaje concreto, lánzalo con safeError() o usa validate().

Subir archivos y ofrecer descargas

Ignacio Peña, de sistemas, exporta cada mes un CSV nuevo de viajes. Ernesto quiere subirlo él mismo a la aplicación, sin esperar a Gabriela, y bajarse los viajes de una estación para revisarlos en una hoja de cálculo. Shiny tiene una entrada y una salida para eso.

fileInput("archivo", "Viajes del mes", accept = ".csv") dibuja el botón para elegir un archivo. Cuando el usuario lo sube, input$archivo no es el archivo: es un data frame con una fila por archivo y las columnas name (el nombre original), size, type y datapath, la ruta temporal donde Shiny lo guardó en el servidor. Se lee desde ahí:

viajes_subidos <- reactive({
  req(input$archivo)
  df <- read.csv(input$archivo$datapath, na.strings = "")
  problemas <- validar_viajes(df, estaciones)
  validate(need(length(problemas) == 0, paste(problemas, collapse = "\n")))
  df
})

Por omisión, Shiny rechaza archivos de más de 5 MB. El de un mes de RiberaBici pesa alrededor de 1 MB, pero el del semestre pasa de 6 MB; el límite se sube al principio de app.R con options(shiny.maxRequestSize = 30 * 1024^2) (30 MB). Subirlo mucho es abrir la puerta a que alguien llene la memoria del servidor.

Un archivo subido es la entrada menos confiable de todas: puede tener otras columnas, otro formato de fecha, filas vacías o estaciones que no existen. La función validar_viajes() del laboratorio revisa eso y devuelve una lista de problemas en palabras del usuario; validate() los muestra.

# R/datos.R: funciones puras para preparar los datos (Shiny carga R/ sola)
limpiar <- function(v) {
  v <- v[!duplicated(v) & v$estacion_origen != "E99" & !is.na(v$fin), ]
  v$inicio <- as.POSIXct(v$inicio, tz = "UTC")
  v$fin <- as.POSIXct(v$fin, tz = "UTC")
  reloj <- v$estacion_destino == "E17" & v$estacion_origen != "E17" &
    v$inicio >= as.POSIXct("2026-05-04", tz = "UTC") &
    v$inicio < as.POSIXct("2026-05-18", tz = "UTC")
  v$fin[reloj] <- v$fin[reloj] + 3600
  v$duracion_min <- as.numeric(difftime(v$fin, v$inicio, units = "mins"))
  v[v$duracion_min >= 1 & v$duracion_min <= 720, ]
}

totales_por_estacion <- function(validos, estaciones) {
  ids <- estaciones$estacion_id
  t <- data.frame(estacion_id = ids, barrio = estaciones$barrio,
                  salidas = as.vector(table(factor(validos$estacion_origen, ids))),
                  llegadas = as.vector(table(factor(validos$estacion_destino, ids))))
  t$balance <- t$llegadas - t$salidas
  t
}

Rendimiento: perfilar, bindCache() y tareas asíncronas
Imagínalo así
En la cocina de un restaurante, el caldo no se prepara cada vez que alguien pide una sopa: se hace en la mañana y se sirve toda la noche. Y cuando un plato tarda cuarenta minutos en el horno, el cocinero no se queda mirándolo: lo deja ahí y sigue atendiendo los otros pedidos. Shiny tiene las dos ideas: guardar lo ya calculado y no bloquear la cocina con un plato lento.
Una aplicación lenta casi nunca es lenta en todas partes: suele haber un cálculo que se lleva el 90 % del tiempo. Antes de optimizar hay que encontrarlo. Perfilar (profiling) es medir cuánto tiempo pasa R en cada función mientras la aplicación se usa. El paquete profvis lo hace con una línea, profvis::profvis(shiny::runApp("app12")): usas la aplicación unos segundos, la cierras y profvis muestra un gráfico de llamas (flame graph), con una barra por función, tan ancha como el tiempo que consumió.
En la aplicación de Gabriela, profvis mostró que casi todo el tiempo de arranque estaba en read.csv() de los 72.283 viajes y en limpiar(). Las dos cosas se hacen una sola vez, cuando el proceso de R arranca, y no en cada sesión: está bien que estén fuera de server. Lo que sí se repetía era otra cosa.
Guardar lo que ya se calculó: bindCache()
El capítulo 11 mostró que un reactive() recuerda su último valor y no recalcula mientras sus entradas no cambien. Pero solo recuerda uno: si el usuario elige Centro, después Mercado y vuelve a Centro, el cálculo de Centro se repite entero. Y cada usuario conectado tiene sus propios reactivos: diez personas mirando Centro hacen diez veces el mismo cálculo.
bindCache() agrega una caché (cache), una memoria de resultados anteriores. Se le dicen las entradas que forman la clave (cache key); antes de ejecutar el reactivo, Shiny calcula una huella de esa clave y la busca. Si está, devuelve el resultado guardado sin ejecutar nada; si no, ejecuta, guarda y devuelve.
intervalo <- reactive({
  mediana_bootstrap(viajes$duracion_min[viajes$barrio == input$barrio])
}) |> bindCache(input$barrio)
Por omisión la caché es de la aplicación: la comparten todas las sesiones de ese proceso de R, así que el segundo usuario que mira Centro recibe el resultado del primero. Vive en memoria con el paquete cachem y un límite de 200 MB; cuando se llena, descarta lo que hace más tiempo no se usa. Con bindCache(..., cache = "session") cada usuario tiene la suya, y con cachem::cache_disk() sobrevive a un reinicio. renderPlot() también acepta bindCache(), y entonces guarda la imagen ya dibujada; Shiny agrega el tamaño del gráfico a la clave por su cuenta.
La regla de oro: en la clave va todo lo que cambia el resultado. Si el cálculo usa input$barrio e input$mes y la clave solo lleva el barrio, la caché devolverá el resultado de otro mes con toda tranquilidad. Y si el resultado depende de un archivo que cambia cada noche, la fecha del archivo tiene que ir en la clave.

No bloquear la cocina: tareas asíncronas
R ejecuta una cosa a la vez. Una aplicación Shiny en un servidor suele ser un solo proceso de R que atiende a todos los usuarios conectados: si uno pide un cálculo de veinte segundos, los demás esperan esos veinte segundos aunque solo quieran mover un deslizador. La caché no ayuda con la primera vez.
La salida es la programación asíncrona (asynchronous programming): mandar el cálculo lento a otro proceso de R y seguir atendiendo. Desde Shiny 1.8.1, la forma recomendada es ExtendedTask: se crea con una función que devuelve una promesa (promise), un valor que todavía no existe pero existirá; el cálculo corre en segundo plano con mirai o future, y cuando termina, las salidas que leen tarea$result() se actualizan.
tarea <- ExtendedTask$new(function(barrio) {
  mirai::mirai(simular_rebalanceo(barrio), simular_rebalanceo = simular_rebalanceo,
               barrio = barrio)
}) |> bslib::bind_task_button("simular")

observeEvent(input$simular, tarea$invoke(input$barrio))
output$resultado <- renderTable(tarea$result())
El botón bslib::input_task_button("simular", ...) se desactiva mientras la tarea corre, para que nadie la lance diez veces. Antes de llegar aquí conviene agotar lo barato: calcular una vez fuera de server, guardar en caché y, sobre todo, calcular menos. El tablero del capítulo 14 no lee los 70.796 viajes: lee un resumen de 2.737 filas preparado antes, y por eso puede correr hasta en el navegador.

Si alguna vez una barra de dentro de server domina, ahí es donde valen la pena bindCache() o un cálculo previo. Los tiempos exactos dependen de tu equipo.


Extender con JavaScript y CSS
Shiny genera HTML, CSS y JavaScript por ti, pero no te encierra. Todo lo que la página necesite y Shiny no traiga se puede agregar, y hay tres niveles.
El primero es la apariencia. bslib, que el capítulo 10 usó para el diseño, cambia el tema completo con bs_theme(primary = "#5b3d8a", base_font = font_google("Inter")), y como Bootstrap está escrito en Sass, los colores se propagan a botones, enlaces y tarjetas. Para un detalle propio, un archivo www/estilos.css en la carpeta de la aplicación se sirve en la raíz de la página y se enlaza con tags$head(tags$link(rel = "stylesheet", href = "estilos.css")).
El segundo es mandar mensajes entre el navegador y R. Desde JavaScript, Shiny.setInputValue("tecla", valor) crea o cambia una entrada que el servidor lee como input$tecla, aunque no haya ningún control en la interfaz. En sentido contrario, el servidor llama session$sendCustomMessage("avisar", list(texto = "Listo")) y una función de JavaScript registrada con Shiny.addCustomMessageHandler("avisar", ...) la recibe:
tags$script(HTML("
  document.addEventListener('keydown', e => {
    if (e.key === 'r' && e.altKey) Shiny.setInputValue('atajo_reiniciar', Date.now());
  });
"))
Con eso, Alt+R reinicia los filtros: el servidor solo tiene un observeEvent(input$atajo_reiniciar, ...). Date.now() asegura que el valor cambie en cada pulsación; si se mandara siempre TRUE, Shiny no vería un cambio y el evento no se dispararía.
El tercero es envolver una biblioteca de JavaScript entera como un htmlwidget, que es como existen leaflet o plotly (capítulo 08). Es más trabajo, y casi siempre ya existe un paquete que lo hizo. El JavaScript en sí está en el curso de JavaScript.


Estructurar el proyecto: golem, rhino o un paquete
Con módulos, funciones de datos, estilos y pruebas, un solo app.R ya no alcanza. Hay tres formas comunes de ordenar el proyecto, y en las tres la idea de fondo es la misma.
  • Carpeta con R/. Es la estructura de la práctica: app.R arriba y en R/ un archivo por módulo y otro con las funciones puras. No exige nada más que Shiny y sirve para la mayoría de las aplicaciones de un equipo pequeño. Se combina bien con renv (capítulo 06) para congelar las versiones de los paquetes.
  • Un paquete de R con golem. golem, de la empresa ThinkR, arma la aplicación como un paquete: tiene DESCRIPTION con sus dependencias, documentación con roxygen2, pruebas con testthat y se verifica con R CMD check. golem::add_module(name = "mapa") crea el archivo del módulo con su esqueleto. Vale la pena si ya sabes hacer paquetes (capítulo 06) y la aplicación va a vivir años.
  • rhino. De la empresa Appsilon, organiza el proyecto con el paquete box, que importa funciones con box::use(app/logic/calculos[resumir]) en lugar de cargar paquetes enteros, y trae Sass, JavaScript con su propio empaquetador, linters y pruebas de punta a punta. Está pensado para equipos grandes, con gente que también escribe frontend.
En las tres se repite lo que hizo Gabriela al partir sus seiscientas líneas: los módulos se ocupan de la interfaz y de la reactividad; los cálculos viven en funciones puras que no saben nada de Shiny. Esa separación es la que permite probar la aplicación sin abrirla, que es el tema del capítulo 13.


La idea clave
Una aplicación Shiny crece sin enredarse cuando se parte en módulos: pares de funciones de interfaz y servidor que se escriben una vez y se usan muchas, cada una con su propio espacio de nombres. Los datos bajan como argumentos y suben como valores de retorno; lo que entra se valida con req() y validate(); lo que cuesta se mide antes de optimizarlo y, si se repite, se guarda con bindCache(). El resto es orden: módulos para la interfaz y funciones puras para los cálculos.


Pruébate
Pruébate
¿Por qué falló la tarjeta copiada tres veces?
Porque los tres desplegables tenían el mismo id, estacion. Un id debe ser único en la página; el navegador y Shiny solo atienden a uno de ellos.
¿Qué hace NS("puerto")("cifras")?
Devuelve "puerto-cifras": le pega el id del módulo delante del nombre, con un guion.
Dentro de moduleServer(), ¿se escribe input$estacion o input[["lomas-estacion"]]?
input$estacion. moduleServer traduce los nombres al espacio de nombres del módulo; por eso el mismo código sirve para cualquier id.
Un módulo de filtros devuelve datos <- reactive(...). ¿Por qué el servidor se lo pasa al mapa como datos y no como datos()?
Porque datos() es el valor de ese instante: el mapa nunca se enteraría de los cambios. Pasando el reactivo, el mapa lo lee con paréntesis y queda conectado al grafo.
¿Qué diferencia hay entre req() y validate(need())?
req() detiene la salida en silencio (queda en blanco hasta que la entrada exista); validate(need()) la detiene y muestra un mensaje que explica qué falta.
Un reactivo usa input$barrio e input$mes, pero tiene bindCache(input$barrio). ¿Qué pasa al cambiar de mes?
La caché devuelve el resultado guardado para ese barrio, que es el de otro mes. Todo lo que cambia el resultado tiene que ir en la clave.
